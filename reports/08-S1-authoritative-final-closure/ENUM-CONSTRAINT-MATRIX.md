# Enum constraint matrix

Stage: 08-S1-authoritative-final-closure · 2026-09-21 · branch `k8s-stg`

Pack basis: `DOMAIN/13-PERSISTENCE-DATA-DICTIONARY.md` ("constraints/index inspection" is stage evidence);
`GOVERNANCE/03` (a closed vocabulary that the database does not enforce is a claim, not a guarantee).

**The rule.** Every closed enum that S1 persists as an integer column carries a database `CHECK` constraint admitting
exactly the defined members of that enum and nothing else. A nullable column additionally admits `NULL`. Before this
stage an integer column typed as an enum in C# accepted any `int` on SQL Server, so "this column holds a member of
this vocabulary" was an application claim with no storage guarantee — and a direct SQL write, a future migration or a
replication path could put `9999` in it.

Naming is mechanical: `CK_{Table}_{Column}_Enum`, generated by
`src/AeroTech.Ordering.Persistence/_Shared/Mapping/EnumCheckConstraints.cs` from `Enum.GetValues<TEnum>()`. The
constraint therefore cannot drift from the enum by hand-editing; it drifts only if someone changes the enum and does
not add a migration, which `dotnet ef migrations has-pending-model-changes` catches.

## 2. Proof

`tests/AeroTech.Ordering.Persistence.Tests/S1/EnumConstraintTests.cs` — 34 tests.

| Claim | Test |
|---|---|
| **Every** persisted enum column in the EF model has a live `CHECK` — the matrix cannot go stale | `Every_persisted_enum_column_is_guarded_by_a_live_check_constraint` |
| Each constraint admits exactly the enum's members, and its null-handling matches the column | `Every_enum_check_constraint_admits_exactly_the_defined_members_of_its_enum` |
| An undefined value is rejected by SQL Server, not by C# | `An_undefined_enum_value_is_rejected_by_the_database` (29 cases) |
| A nullable enum column still accepts NULL | `An_optional_enum_column_still_accepts_null` |
| A nullable enum column still rejects an undefined value | `An_optional_enum_column_still_rejects_an_undefined_value` |
| A defined value is still accepted | `A_defined_enum_value_is_accepted_by_the_database` |

The first two tests walk the live EF model (`DbContext.Model`) and the live `sys.check_constraints`, so they cover
columns nobody remembered to list here. This matrix is a readable rendering of what those two tests enforce, not the
source of truth.

The 29 behavioural cases issue raw `UPDATE … SET [col] = 9999` against SQL Server, bypassing the domain and EF, and
assert error 547 naming the exact constraint.

**Red-first evidence.** `Every_persisted_enum_column_is_guarded_by_a_live_check_constraint` failed on its first run
with two real gaps that the hand-written list had missed:

```
["Operations.CommandReceipts.CommandKind (OrderingCommandKind)",
 "Order.OrderPreparations.AcceptanceAssurance (AcceptanceAssurance)"]
```

Rows 38 and 39 exist because that test was red. The constraints were added, the migration regenerated, and the test
then passed.

## 3. Not guarded, and why

| Column | Why |
|---|---|
| `Orders.SalesContext` office/seller **identifiers** (`SellerId`, `SellingOfficeId`) | They are reference-data identities, not a closed vocabulary. Their validity is owned by ReferenceData; a `CHECK` would hard-code another service's data. |
| Every `string` reference (`SourceOfferId`, `BoundId`, `SettlementCategoryCode`, …) | Deliberately opaque — `DOMAIN/03` requires a settlement category to be preserved and never interpreted. A value set would be interpretation. |
| `PricingLineRole` beyond `Original` in S1 data | The column is guarded (row 29) for all four members. S1 only ever writes `Original`; the other three are reachable from later stages and are admitted now so that no later migration has to widen the constraint. |

## 4. Interaction with the semantic CHECKs

These 39 vocabulary constraints sit alongside the pre-existing semantic CHECKs, which are not mechanical and encode
Pack rules rather than enum membership:

`CK_PricingLines_TaxNotSettlement`, `CK_PricingLines_CommissionNotCustomer`, `CK_PricingLines_OtherInformational`,
`CK_PricingLines_SettlementAttribution`, `CK_PricingLines_Direction`, `CK_PricingLines_OriginalMagnitude`,
`CK_PricingLines_SaleMagnitude`, `CK_OrderItems_AcceptedTotal`, `CK_OrderComponentTotals_Magnitudes`,
`CK_FundingObligations_ExactlyOneScope`, `CK_FundingObligations_Amount`, `CK_FundingObligations_Version`,
`CK_OrderChanges_CommercialVersion`, `CK_PriceChangeSets_FinancialSequence`, `CK_OrderJourneys_Sequence`,
`CK_OrderSegments_Sequence`, `CK_FarePricingUnits_Sequence`, `CK_OrderTravellers_Guardian`,
`CK_OrderPreparations_Digest`, `CK_Orders_Root`.

A vocabulary constraint says the value is a member of the enum. A semantic constraint says the combination is legal.
Both are needed; neither substitutes for the other.
