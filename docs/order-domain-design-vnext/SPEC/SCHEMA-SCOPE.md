# Schema scope and normalization contract

`openapi-s1.json` specifies all four sale surfaces for S1 and their common direct JSON result objects. It is not a claim that the current repo exposes those routes. The implementation must emit a generated runtime OpenAPI in each stage bundle and test conformance. API-CONTRACTS and commands.json cover later command routes; each active stage must extend the runtime schema with its typed body/result, not return anonymous blobs as a substitute for design.

The normalized candidate schema is a transport/container shape. Product-specific `details`, fare-construction units and permission-filtered OrderDetails require the corresponding domain schema/validator described in DOMAIN. Their structural JSON objects are not permission to accept unregistered products or omit relationships. Validate referential integrity, exact price sign/effect, allocation/coupling, quantity and source authority in the domain/application mapping. A source wire shape and a normalized target shape are distinct.

Canonical hashing: use a versioned envelope, UTF-8, deterministic object-key order, invariant decimal strings, complete immutable identity/scope/profile fields and a defined order for each semantic sequence. Sets are sorted by stable identity; flight/coupon/pricing occurrence sequences preserve meaning. Absent and explicit null handling is fixed per schema version. Do not hash arbitrary serializer output, mutate request fields after persisting the hash, or use a numeric total alone as accepted binding. The exact canonicalization algorithm and tests are frozen in S1 before accepting the first Order.

Later fields requiring exact implementation naming must be settled in the active slice PLAN as a conforming representation choice, with schema/tests, not an invented business decision. New identity/ownership/economic/authority meaning needs the formal semantic change record. This distinction prevents both needless design workshops and silent semantic drift.
