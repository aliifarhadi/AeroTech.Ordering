# S1 runbook — real AirOffer candidate to local Order

This runbook defines the acceptance behavior for S1. It does **not** prescribe local scripts, SQL Server location, authentication test issuer, evidence folder or service-launch tooling. Use the repository/team-approved execution mechanism.

## Preconditions

- B0 semantic/technical guarantees are satisfied.
- A valid priced AirOffer candidate can be obtained through the approved AirOffer environment when running the live-candidate portion.
- Ordering's AirOffer adapter is configured through the existing application configuration convention.
- Missing owner guarantees remain marked by their `BLOCKED_DECISION`; a real response does not automatically certify immutability/validity semantics.

## 1. Prepare before acceptance

Call the S1 preparation endpoint with a real priced OfferId using the approved caller/authentication context.

Verify the normalized candidate contains the source identities and commercial facts required by S1, including the priced snapshot, traveler/source references, itinerary/segment facts, item/service source boundaries, monetary lines, fare-construction evidence where supplied, source digest/provenance and every known owner validity/assurance field.

Record the real owner request/response mapping with secrets/PII removed. A recorded fixture is not a live proof.

## 2. Explicit acceptance and Create

Create the Order by referencing the exact stored preparation plus the exact accepted digest/version evidence required by the S1 API contract. The Create command must not accept a client-recalculated price.

Verify:

- exactly one Order is committed;
- `CommercialVersion = 1`;
- accepted source/pricing facts equal the prepared snapshot;
- OrderItem/OrderService identities and beneficiary/coverage mapping satisfy DOMAIN invariants;
- the local `OrderDetails` projection is immediately readable according to the chosen transaction/projection implementation;
- Create causes **zero** FlightFlow, JetPay, document-issuer or Ledger synchronous calls;
- Create does not call AirOffer/AirPrice again if the S1 design says acceptance consumes the stored prepared candidate.

## 3. Idempotency and preparation consumption

Exercise the canonical public mutation semantics:

1. same idempotency key + same semantic request -> same Order/result, no duplicate mutation;
2. same key + different semantic request -> conflict according to the existing framework error convention;
3. a consumed single-use preparation cannot create another Order unless the design explicitly marks that preparation reusable;
4. concurrent creation attempts cannot produce duplicate Orders or duplicated pricing graphs.

Replay must be proven by durable-receipt evidence and by showing that no owner/network call occurs. If the existing framework/user-approved API convention already exposes replay metadata, use it; otherwise no client-visible replay flag/header is required and no `BLOCKED_DECISION` is created solely for replay signaling.

## 4. Restart and owner outage

After Order creation, restart Ordering using the approved environment mechanism. Make AirOffer unavailable to Ordering using an approved test mechanism and verify:

- GetOrder still succeeds from local Ordering read data;
- committed Create replay still resolves locally without re-contacting AirOffer;
- projection rebuild, if exercised, reproduces the same semantic OrderDetails without changing CommercialVersion/financial sequence or calling an owner.

## 5. Live-candidate status

A real AirOffer candidate reaching Prepare/Create/Get proves only the observed live-candidate path. If AirOffer does not provide the immutable acceptance/version/expiry guarantees required by BD-001, record the live-candidate proof separately and leave BD-001 open. Never upgrade an observed sandbox/current endpoint into a stronger owner contract by inference.

## Pass

S1 passes its local/reference acceptance only when the S1 invariant/scenario set passes. Live owner certification is separate and requires the exact owner guarantees named in the contract/blocker documents.
